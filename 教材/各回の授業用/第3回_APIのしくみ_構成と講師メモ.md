## 04 APIは、決まりに沿って話す窓口

人には言葉で、プログラムには決めた書式で頼む

- どこへ頼む？＝URL（行き先の住所）
- 何をする？＝GETなどの頼み方
- 何が返る？＝結果や、うまくいかなかった理由

講師メモ：APIはプログラム同士の接点。受付は役割の例えで、人が応答しているわけではない。返事の形式や使える操作はAPIごとに違う。
参照：授業の説明・例え・練習用の仮定

講師メモ：サーバーは画面のお願いを処理して返事を返す。画面は受け取った情報を表示に使う。失敗の返事が返る場合もある。

## 06 GETとPOSTは、頼み方の種類

GETは「見せて」、POSTは「送るので処理して」

- 例：問題の一覧を見る
- この公開APIで使える
- 一般例：申込内容を送る
- この公開APIでは使えない

講師メモ：POSTが必ずDBを更新するとは限らない。GETは読み取りの意図の操作。このハンドラーはGET以外を405で拒否する。学習履歴用のPOST APIは公開していない。
参照：lib/public-api.mjs:13

## 07 このアプリの窓口は3種類

窓口の行き先を「エンドポイント」と呼ぶ


やりたいこと / GETで頼む行き先
問題一覧を見る / /api/catalog
1問を見る / /api/questions/2026-001
正答・説明を見る / /api/questions/2026-001/solution

講師メモ：2026-001はURLの例。DBに公開対象の該当問題が存在するかは未確認。2025年度も同じ形式。catalogは目録だけで、問題文や正答をまとめて返すものではない。
参照：lib/public-api.mjs:18-37

## 08 JSONは、共通の書式で書いたメモ

「項目名：値」で、何の情報かが分かる


```text
{
  "id": "2026-001",
  "year": 2026,
  "number": 1
}
```
- id＝問題のID ／ year＝年度 ／ number＝問番号

講師メモ：説明用に項目を抜粋した有効なJSON。実際の単問応答にはdomain、prompt、choicesも含まれる。文字は二重引用符で囲み、数値は囲まない。返事の文字列を画面側でオブジェクトとして読み取る。
参照：lib/public-api.mjs:31-37

## 09 返事には「状態の番号」もある

荷物の「配達完了・宛先不明」のような目印


番号 / このAPIでの意味
200 / 情報を返せた
404 / 行き先が対象外、または問題がない
405 / GET以外の頼み方は受け付けない
500 / 取得処理の途中で問題が起きた

講師メモ：HTTPステータスと呼ぶ。このハンドラーでの振る舞いを記載。500だけではDB停止など原因を断定できない。ネットワーク断ではHTTPの返事自体が来ないこともある。
参照：lib/public-api.mjs:13-40

## 11 通信を見る準備：Networkを開こう

Network＝ブラウザの「やり取りの記録」

- 先生が用意した練習用アプリを開く
- ブラウザの開発者ツールを開く（F12など）
- Networkを選び、Fetch/XHRで絞る
- 画面を読み直して、catalogを探す

講師メモ：ブラウザや端末によって表示名・開き方が違うため講師が補助。接続先URLとデータの準備が必要。既存の本番サイトを前提に起動・接続させない。catalogはメモリに保持されるため、画面の再読み込みで最初の取得を観察する。
参照：public/learning.mjs:26-38

## 12 練習1：一覧のお願いと返事を読む

catalogを選び、3つを記録しよう

- Request URL：どこへ頼んだ？
- Request Method と Status：GET？ 何番の返事？
- Response：questions や count はある？

講師メモ：URL、GET、200、questionsとcountなどが観察ポイント。ただし実際の状態はその場の画面で判断する。問題数を200と決め付けない。個人情報や認証情報をAIへ貼らず、必要な項目だけ使う。
参照：lib/public-api.mjs:18-27

## 13 練習2：1問を開いて、通信を追おう

「問題を見る」と「答えを見る」を分けて観察する

- 問題を1問開く。questionsの通信を探す
- 回答して、solutionの通信を探す
- URLと、返った項目の違いをメモする
- 通信がなければ、画面を読み直してやり直す

講師メモ：取得済みの問題はquestionCacheから返る場合がある。解説はsolutionで取得。公開APIはsolution URLへの直接GET自体を拒否しないため、「サーバーが回答前の取得を防ぐ」と教えない。画面の操作順とアクセス制御を区別する。
参照：public/learning.mjs:32-38,117-145; lib/public-api.mjs:29-37

## 14 答え合わせ：返す項目が違う

問題だけの返事に、正答は入っていない

- prompt：問題文
- choices：選択肢
- id・年度・分野など
- answer：正答の位置
- explanation：説明

講師メモ：単問応答とsolution応答の実装上の違い。UIは通常回答後にsolutionを呼ぶが、URLに対する取得認可を意味しない。sourceやreviewerなどの元データは返さない。
参照：lib/public-api.mjs:31-37

## 17 直したら、お願いと返事をもう一度確認

文章が変わっても、情報の取り方は変えない

- 変えた文が出る失敗ケースを、先生と再現する
- 分かる文になったか、画面で確かめる
- 成功時は、問題と選択肢が今までどおり出るか見る
- 変更前後を比べ、予定外の変更がないか見る

講師メモ：既存DB・本番環境には変更しない。練習用コピー・合成応答で確認する。HTTPの失敗応答とネットワーク自体の失敗では通る分岐が異なる点も講師が説明。テストを作る場合は期待する文と既存の正常動作を確認する。
参照：授業の説明・例え・練習用の仮定
